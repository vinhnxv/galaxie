# ADR-0028: Decision model roles through the model router

- **Status:** Accepted (maintainer decision, 2026-11-08), for the request and answer contract, the structured-output provider and the confidence gate. No dedicated decision model is chosen or recommended.
- **Date:** 2026-11-07
- **Related:** brief §3.3, §9.4, §9.7, §10.3–§10.6, §18; ADR-0006, ADR-0012, ADR-0014, ADR-0016, ADR-0017, ADR-0021
- **Revisions:**
  - 2026-11-08: accepted after the modality, mock, structured-output provider and gate merged. Everything below about dedicated models stays a proposal: the measurement spike has only run with a mock, and real-model confidence is unmeasured.

## Context

Routing, triage and extra guardrail questions ask for a bounded decision about a state: which route, whether to ask, or a score on an ordered scale. A text role can answer these through JSON, but still pays the latency and token cost of generation and needs output validation. Unconstrained text also permits answers outside the offered choices. Dedicated decision models promise a single forward pass instead; those promises do not establish browser performance or accuracy on galaxie's questions.

The [brief's per-role routing](../galaxie-project-brief.md#103-per-role-routing-and-first-run-order), [schema-directed inference](../galaxie-project-brief.md#106-mvp-inference-path) and [budgets](../galaxie-project-brief.md#94-budgets) provide the integration point. [ADR-0006](0006-model-providers-and-routing.md) owns routing; [ADR-0012](0012-security-baseline.md) and [ADR-0014](0014-data-labels-and-argument-shapes.md) constrain every destination and action. [ADR-0021](0021-in-browser-onnx-chat-provider.md) concerns ONNX **chat** inference, not arbitrary ONNX decision heads. The [brief's evidence rules](../galaxie-project-brief.md#18-verdict-demonstrations-and-engineering-checks-adr-0016) make model and device metrics demonstrations, not framework quality guarantees.

## Decision

### Framework-neutral request and answer contract

Add a `decision` modality whose request is `{ state, questions }` and whose result is `{ answers, usage? }`. The shape borrows the state-plus-named-questions organization of d1's `system_one(state, questions)`, not its Python types, model identity or wire protocol. Core owns the public types and validation without importing a model runtime or agent framework.

`state` is text or another JSON value: null, booleans, finite numbers, arrays and plain objects containing JSON values. Reject cycles, accessors and non-JSON values rather than silently dropping or converting them. No image, video or other media input is introduced in this version. `questions` is a plain object of unique, non-empty question names. Every question has `type` and text `instructions`; type-specific fields and answers are:

| Question | Additional request fields | Required answer `value` | Optional `probabilities` |
| --- | --- | --- | --- |
| `boolean` | None | A boolean | A complete distribution keyed by `yes` and `no`; `probabilities.yes` is the probability of yes. |
| `choice` | `options`: an object mapping at least two distinct option keys to their descriptions; `multiple` defaults to `false` | One listed option key | A complete categorical distribution keyed by the listed options. |
| `choice`, `multiple: true` | The same `options` | An array of distinct listed option keys; an empty selection is allowed | For each listed option, a separate `{ yes, no }` inclusion distribution. |
| `score` | `min` and `max`: safe integers defining 2 to 10 ordered levels, inclusive, with step 1 | An integer from `min` through `max` | A complete categorical distribution keyed by each level's decimal string. |

Each answer is `{ value, probabilities?, confidence? }`, interpreted against its named question. `confidence`, when present, is finite and in [0, 1], and describes the provider's confidence in the returned decision, not an authorization. All probabilities are finite and in [0, 1]. Each categorical distribution, including each multi-select option's yes/no pair, must sum to 1 within an absolute tolerance of `0.000001`. Multi-select inclusion probabilities across different options need not sum to 1: several options can be true. A dedicated provider must map its native marginals to these pairs, not normalize unrelated labels into a categorical distribution.

Probability distributions and confidence are optional independently. A boolean without a distribution is valid, but supplies no probability of yes. The structured-output provider below supplies values only; it must not invent probabilities or turn a generated number into confidence. The mock can supply both for exercising thresholds. No confidence is inferred from an option distribution automatically.

Require exactly one answer for every question, with no extra question names or unknown answer fields. Reject an unknown option, duplicate selection, out-of-range score, missing answer, malformed probability distribution or malformed confidence with the existing fixed `invalid` error from [errors.ts](../../packages/core/src/errors.ts), without including state or reply text. Return no partially validated answers. Output validation belongs before the executor or host consumes the result.

Use a fixed first-version cap of **16 questions per call**, matching the trained set size documented by the only dedicated candidate that states one. Reject an empty or oversized set with `invalid`; do not truncate or silently batch. Reuse `RunBudget.payload` and the host's finite `payloadBytes` limit, default **1,048,576 UTF-8 bytes**, for the whole request and the whole answer. This also caps the serialized state, including JSON encoding overhead, within that request; it is a byte bound, not a tokenizer context claim. Exceeding it is `budget_exceeded`. Providers must additionally reject inputs beyond their own context limits without truncation. This extends the existing payload-budget mechanism to decision calls; it does not claim text prompts already pass through it.

Defer text, number, date, box and boxes question types. They are extraction rather than bounded decisions and widen both the output surface and the validation needed. A score is an advisory model judgment, never authoritative grading or a transaction (ADR-0012).

### Modality, routing and accounting

Extend `ModelRoleRequirements.modality` and `ModelDescriptor.modality` with `decision`. An agent will declare, for example, `models: { 'triage.route': { modality: 'decision' } }`. The host will register decision descriptors in `ModelRouting.providers` and map that role to decision provider IDs in `ModelRouting.roles`, alongside its destination allowlist and reservations. This is the same routing table compiled by `ModelRouter` today, not a separate decision router.

Preparation must reject a role whose listed provider has a different modality. Selection and per-call requirement matching must also enforce exact modality equality. A decision role never dispatches to a text descriptor, and a text role never dispatches to a decision descriptor. An unsupported decision request is not a reason to fall back to text or to another provider after dispatch.

Every inference attempt obtains the existing `ModelPort.begin` lease. Preserve readiness/download consent, destination notices, per-call credentials, cancellation, live labels, shared destination consent, token/cost reservations and output-safety outcomes. Before release, pass the complete validated answer serialized as JSON through `lease.checkOutput(..., { final: true })`; the structured-output path also retains the checks on its generated reply. No partial decision stream is introduced. An absent output hook remains absent, as with text calls; a blocked or failed hook must prevent publication. State and questions enter the same sticky run-label context as other model input. A `private-user` state therefore blocks a third-party decision provider under the default policy, even if the role lists it and the user has consented, exactly as for text. Consent cannot widen the label policy, and a selected option cannot shed labels for subsequent calls.

Choose **provider-reported token usage**, not question count, as the accounting unit so the existing token and cost budgets remain meaningful across both provider kinds:

- Reserve before dispatch using the existing formula: `maxTokens` tokens and `maxTokens * max(inputPerToken, outputPerToken)` for known pricing, or the required `maxCost` for unknown pricing. Preserve the current rule that `maxCost` is supplied if and only if some provider in the role's list has unknown pricing. The host sizes the reservation for the entire serialized input, questions included, and any generated reply; `maxTokens` is a reservation and the output limit passed to providers that accept it, not a measured input count.
- A dedicated forward-pass provider reports `ModelUsage { inputTokens, outputTokens: 0 }`. Input includes state, questions and the provider's packed representation, including repeated state in multiple packed rows. Decisions themselves are not generated tokens and question count is not converted to fictitious tokens. A structured-output provider reports the underlying chat model's actual input **and generated output** tokens. Its implementation still generates text even though its public modality is `decision`.
- On successful completion call `lease.end(usage)` once. Valid, non-aborted counts replace the token reservation with `inputTokens + outputTokens`; known prices settle their weighted sum. Missing/invalid usage charges `maxTokens`, unknown pricing charges the cost reservation, and failure/abandonment calls `lease.fail()` once at the reservation. Failures inside `begin` before lease issuance release the reservation; once issued, a failed lease charges the reservation even if inference did not start. Retain over-budget settlement behavior and the host-proxy spending limit; cancellation is not proof billing stopped.
- Reuse the bounded repair policy for invalid answers: route `repairAttempts` defaults to zero and every retry consumes the shared run repair allowance and a new ordinary lease. Extend the validation-to-repair path to decision results, including semantic checks that JSON Schema alone cannot express. No unbounded provider-internal retries or free repairs. Exhausting the route's retry allowance returns fixed `invalid`; the confidence gate takes its conservative path rather than accepting a partial result. Cancellation or shared run budget exhaustion still stops the run.

### Providers, in delivery order

1. **Deterministic mock.** Build a decision mock alongside the existing scripted chat mock for tests and demos. Script typed choices, boolean answers, scores and optional confidence/distributions; valid fixtures sum to 1 under the rules above. Include deliberate invalid replies for rejection and repair tests. It performs no inference or network request and provides no evidence of real-model accuracy.
2. **Structured output over an existing chat model.** Build a decision provider wrapper for any already-routed chat model that advertises and implements `structured-output`: WebLLM, Built-in AI or a suitable remote model. Convert the whole question set into one closed JSON Schema object with every named answer required: booleans, enum option keys, unique arrays of enum keys for multiple choice, and integer score levels as enums. Call the model's structured-output path once, validate the reply, then map fields to the decision answers. Supply **no confidence and no probabilities**, even if the model volunteers them. This needs no additional model download: it reuses a model already available to that host. Built-in AI's available path is the zero-download baseline; preparing an unavailable browser-managed model is still a host download step.
3. **Dedicated models only after measurement.** Do not ship or recommend any of the candidates below before the measurement spike has run and the maintainer has reviewed the evidence. An ONNX export does not establish compatibility with ADR-0021's chat generation loop. Galaxie ships no model weights.

For the structured-output wrapper, the host registers an explicit **decision** provider ID over a selected chat provider factory/runtime; its descriptor preserves that source's final destination, languages, pricing, credential and readiness/download requirements. It does not list a text provider as a fallback for the decision role. The wrapper uses the selected decision lease for the underlying structured inference and its output checks and settlement; it must not open a nested text-role lease and double-reserve or double-charge the same inference. Each repair is a separately leased attempt. Reuse the existing schema and repair conventions while keeping framework types outside core. The wrapper is new work, not an API already exposed by `MockChatModel` or `ModelRouter`.

The d1 card allows more than 16 questions over a state and describes a speed/accuracy tradeoff when increasing its trained question-set size. ### Optional confidence and the conservative gate

An answer without confidence is valid. A provider's number is not trusted merely because it is in [0, 1]. The host must calibrate confidence on its own questions and relevant domains before enabling a threshold. The [d1 card](https://huggingface.co/LiquidAI/d1-2B) advises: “Calibrate any decision threshold on data from your own use.” [WaterSheep](https://huggingface.co/samratduttaofficial/WaterSheep) likewise advises own-data validation, and its own held-out numbers show calibration error increasing outside its training-like distribution. Neither establishes a transferable threshold for galaxie.

Build a host-configured confidence gate that can request an **additional** confirmation or interaction. Its threshold and any calibration mapping come only from trusted host configuration, never model output, question instructions or untrusted state. The threshold is finite and in [0, 1]. Only a valid answer with host-calibrated confidence at or above that threshold may avoid this additional question; it cannot avoid any already-required question or confirmation. For a gate over several answers, every answer it depends on must meet that condition. A missing, malformed, uncalibrated or low-confidence answer asks the user. **No confidence always asks**, including every structured-output answer. A model decision can still advise routing without a confidence gate, subject to all ordinary policy checks.

### A decision can add a confirmation, never remove one

Capability confirmations, write confirmations, ADR-0012 checks, URL policy and existing required interactions are not inputs a decision is allowed to waive. Keep these deterministic controls in their current owners. In particular, neither a high-confidence answer nor a selected option can change a binding's approval requirement, synthesize an approval, consume one for another effect or alter label/consent policy. An extra gate asks through the existing host confirmation or registered interaction paths; it does not render model-provided approval UI.

A decision answer is model output and may be influenced by untrusted content in its state. Even a correctly parsed, high-confidence answer can be wrong or injected. It cannot lower the labels, destination restrictions or consent requirements of what follows. Low confidence or invalid/missing output takes the ask-user path while normal cancellation, denial and exhausted budgets still prevent unauthorized or further model execution. This adds no probabilistic substitute for ADR-0012 and no permission to make authoritative scores client-side.

Extend the [injection corpus](../../tests/injection-corpus/README.md) with untrusted states that demand skipping confirmation, forge a threshold/approval or claim a write is harmless. Drive the mock to obey those instructions, including returning a syntactically valid high-confidence answer. Required confirmations must still appear and declining them must prevent invocation; URL and label/consent checks must still block their respective paths. Assert SDK-controlled outcomes, not whether a model resists the payload.

### Host license review

Galaxie does not redistribute weights. **Each host is responsible for the license of every model it loads**, including run-time downloads. When a decision model is added to a catalog or documentation, display its license next to its name and pinned revision, distinguishing weight and code licenses where they differ.

The [LFM Open License v1.0](https://www.liquid.ai/lfm-license) was read on **2026-11-07**. Its page summary places the commercial restriction above $10 million USD annual revenue, while the threshold definition includes exactly $10,000,000 as well. Do not silently resolve that wording difference. The threshold covers the entity and entities controlling it, controlled by it or under common control, with control defined by ownership of 50% or more. Research and non-profit use is exempt. Commercial use above the threshold is outside this license and requires a commercial license from Liquid AI; a host at exactly the threshold must also resolve the inclusive definition with the vendor before relying on commercial rights.

Distribution obligations include providing recipients the license, marking modified files, keeping notices and handling any NOTICE file. The license has no copyleft requirement and grants no trademark rights; non-compliance terminates it. The cited terms do not state how an app downloading weights at run time differs from bundling them, or whether end users count toward revenue. These questions, the threshold wording and applicability to the host need a host-side license review. This record is an engineering inventory, not legal advice. Apache-2.0 repository code does not determine the rights to a model it loads.

### Measurement before recommending a dedicated model

Keep the measurement spike outside `packages/`; its code never becomes package implementation. Its real-device run is a maintainer step. Before that run, write down the device/browser profile, functional checks, proposed recommendation pass bar and question set in the spike plan. Accuracy and calibration targets inform a model recommendation only; results remain demonstrations under ADR-0016, not framework pass/fail quality gates, security guarantees or promises about another host's questions.

Pin model/export revisions and every downloaded file's hash, tokenizer, packing/decoding code, runtime and quantization configuration. Compare:

- Load time from a warm cache, separately from download time.
- First-decision latency for the four combinations of **200 and 1,000 state tokens** with **10 and 30 questions**, reporting tokenization and end-to-end timing boundaries. At the proposed core boundary 30 questions means two explicit caller requests of 16 and 14; report aggregate latency and repeated-state cost. Any additional native 30-question experiment must disclose its row packing and stay separate from the supported core contract.
- GPU memory with and without a loaded chat model, recording both the decision model alone and coexistence cost; record unsupported configurations rather than assuming they fit.
- Accuracy and expected calibration error on about **200 galaxie questions**, with labeled answers, domain/type breakdowns, ECE binning and held-out calibration/evaluation splits declared in advance. Report uncertainty and missing confidence; do not fabricate ECE for a provider that reports none.
- Agreement between the browser quantization and the pinned reference on the same questions, separately from accuracy against labels. Record any reference that cannot run and the resulting evidence gap.
- The structured-output decision provider over the **available Built-in AI zero-download path** as the baseline, including its generated-token cost, schema failures, latency and always-ask behavior. It supplies no confidence, so confidence/ECE is not applicable. Record the browser version and availability because its managed model identity cannot be pinned.

Supply a mock-backend run of the spike to verify packing/batching boundaries, measurement collection and report generation without downloading weights or requiring a GPU. It is harness evidence only. No dedicated candidate becomes recommended merely by having an export or completing that mock run.

### Open maintainer decisions

The proposed work has **three implementation pieces behind one modality**: core contracts/routing plus the mock, the structured-output provider, and the confidence gate. The measurement spike is separate. Whether to keep that division and whether the spike stays are maintainer decisions; implementing pull requests must explicitly say they proceed as written or identify a revised decision. This Proposed record settles a buildable default, not those maintainer choices.

The only documented dedicated candidates here that can supply confidence or probabilities have limited maturity/evidence: WaterSheep is 0.1.0 and the Laya conversion has one commit, while the vendor d1 model's license limits commercial eligibility. None has measured browser accuracy or calibration on galaxie's question set in this record.

## Alternatives considered

- **Keep plain text roles with JSON output.** Leaves decision semantics, option validation and probability handling implicit; retain chat inference as an explicit structured-output decision provider instead.
- **A separate package outside the router.** Duplicates or bypasses labels, consent, budgets and lease ownership; core owns the modality and existing provider boundaries own inference.
- **Ship a dedicated model first.** Commits download, packing and license costs before browser/domain evidence; start with mocks and already-loaded structured-output models.
- **Classifier endpoints on a backend.** A host may explicitly route a later decision provider there, but requiring one adds a backend and sends state off-device; it cannot replace the local path or policy checks.
- **Skip confidence entirely.** Works for structured output but discards useful calibrated evidence from future providers; make confidence optional and absence conservative.

## Consequences

- A new public modality, request/answer types and provider contracts will need implementation and compatibility documentation. Core owns modality matching, validation and policy; providers own model-specific packing and inference.
- The next pieces build core plus the deterministic mock, the structured-output wrapper and the additive confidence gate. The spike supplies evidence before any dedicated model is shipped or recommended; this proposal implements none of them.
- Reusing an existing chat model avoids another download but still generates tokens. Without calibrated confidence, every confidence gate asks, adding interactions and user effort.
- Hosts retain license diligence, domain calibration and backend authorization/spending obligations. Vendor licensing and multi-gigabyte downloads may rule out otherwise functional candidates.
- No extraction types, automatic batching, new media contract, model weights, independent decision router, policy bypass or quality guarantee are introduced.
