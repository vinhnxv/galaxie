# Security review

This review maps the implemented SDK-controlled paths to [ADR-0012](adr/0012-security-baseline.md), the OWASP Top 10 for LLM Applications (2025), and [brief §9.7](galaxie-project-brief.md#97-mandatory-security-baseline-invariant-adr-0012). It covers the branch's source and automated tests, including the 34 synthetic [prompt injection cases](../tests/injection-corpus/README.md). It is not a model-quality evaluation or a claim about arbitrary host applications.

The threat model assumes a fully compromised model. The corpus's obedient-attacker mock follows each injected directive; the real router, broker, interaction policy and MCP client must constrain the resulting action. The corpus targets Node and headless Chromium with mock providers. The two LangGraph.js tool-loop cases use mock models on both lanes. No real-model result is claimed. The corpus covers every combination of lesson, tool output and MCP-description vectors with unapproved-write, egress, URL-render, label-downgrade and instruction-in-data goals. MCP descriptions are not normally supplied to agents: the fixture deliberately supplies synthetic metadata to the attacker and separately checks pin invalidation against its own loopback server.

The boundary is trusted-first ([ADR-0002](adr/0002-trusted-first-execution.md)). There is no sandbox. A trusted agent, host, XSS payload or dependency that calls browser APIs or its own model directly can bypass SDK policy. Backend authorization, reviewed dependencies and host CSP remain necessary. A broker binding's declared destination must describe the final recipient, including forwarding by a proxy.

Opt-in [development warnings](system-design.md#development-warnings) are an integration aid, not a control. `RuntimeOptions.developmentWarnings` reports missing page enforcement, optional unbound capabilities, roles without a usable provider, provider-key-shaped storage values and blocked interaction URLs using codes and trusted identifiers only. The absent option runs no checks or extra availability probes. Page probes cannot inspect response headers, cover every CSP directive or find every credential; report-only policies can still warn, and a pass-through Trusted Types default policy is a known false positive. Enforced probes produce expected console violations and browser reports if configured. Warnings never remediate or change routing, bindings or rejection policy. Existing host-only `DiagnosticEvent.error` rules also apply to thrown instance warning callbacks; raw callback failures must not be exported as content-free warnings. See the [Node coverage](../packages/core/test/development.test.ts) and [Node/Chromium mock-model coverage](../tests/conformance/development-warnings.test.ts).

## Brief §9.7 B and C duties

This table separates SDK mechanisms from the work that an integrating host or agent author must perform. The baseline table gives the source and test evidence for each corresponding identifier.

| Duty | SDK contribution | Who must act and what remains |
| --- | --- | --- |
| B1. Authorize every backend request | Broker grants, validated inputs and attribution context (A2/A8). | Host backend: authenticate the principal, authorize each object/operation and enforce scopes. Attribution is not authority. |
| B2. Strict CSP and Trusted Types | Text-only supplied components and URL checks (A1); example CSP (B2). | Host: send effective CSP/Trusted Types policy, review all sinks and constrain connections/media/forms. Allowed endpoints and navigation still need review. |
| B3. No bundled provider or tracing credentials | Call-scoped credentials and allowlisted tracing (A4). | Host: proxy remote providers, keep secrets server-side, register a host collector/exporter and audit shipped bundles. |
| B4. Narrow capabilities and idempotency | Named schemas, effect IDs and optional recovery journal (A2/A3/B4). | Host: choose narrow operations, derive trusted identities and honor idempotency keys at the backend; reconcile unknown outcomes. |
| B5. No password/payment components | Only registered components can resolve (A1/B5). | Host: review every catalog entry and prohibit credential/payment collection. The SDK cannot determine component semantics. |
| B6. Controlled MCP servers | Namespaces, allowlists, metadata pins, scoped sessions and limits (A9/B6). | Host: operate/control the server or gateway, authorize each call and re-approve metadata deliberately. |
| B7. Only reviewed bundled agents | Manifest/schema generation and byte-integrity verification (B7). | Host: review agent/dependency code and deliver trusted build output. No loading arbitrary agent URLs or treating manifests as isolation. |

| C3. Effects after interrupts/confirmations | Native graph semantics, effect IDs, confirmation gate and optional recovery (C3/A5). | Agent author: order effects after pauses and handle re-execution/idempotency explicitly. |
| C4. Treat tool/retrieval results as data | Broker/router/interaction controls, the fixed corpus graph and LangGraph.js `capabilityTool` write-policy checks (C4). | Agent author: execute model-chosen calls through the helper and broker with explicit node config; preserve host confirmations, labels, budgets and recovery scopes. Set `ToolNode` error handling to false so fatal failures propagate. Review custom tools, project display/output data and treat retrieved instructions as untrusted. |

The corpus's `url-query-on-allowlisted-origin` case is a documented limit, not an expected failure: an interaction containing `https://example.test/lesson?note=synthetic-query-value` becomes pending. `isAllowedUrl` still checks origin, protocol and user information. Core's internal run-aware check additionally rejects registered private strings in raw and twice percent-decoded URL candidates, with `+` treated as a space. When whole-string decoding fails, each maximal run of valid percent escapes is decoded independently; invalid UTF-8 runs stay raw on both passes. The same forms of the parser-normalized candidate are checked, closing literal tab/newline/carriage-return reconstruction at core pending/event publication. The standard React registry independently rejects literal whitespace. Matching shares the broker's normalization and eight-character registration minimum. The guard is skipped when `private-user` policy allows `third-party`, because following a link can reach an arbitrary site; origin checks still apply. The corpus query uses a synthetic unregistered value and still passes unchanged. Hosts must constrain URL templates and remaining values before display. [Separate Node/Chromium tests][private-url-tests] cover accepted private payloads with the obedient-attacker mock and a framework-neutral executor; [core tests][private-url-unit-tests] additionally cover paths, policy opt-out and restore from saved submissions. Historical submission text is conservatively registered on restore because it lacks schema identity; strings held only in prior input, capability outputs or arbitrary checkpoint state cannot be reconstructed. The broker uses the same shared decoding for every argument string and key when private-user policy disallows its binding destination ([label tests][label-tests] and [Node/Chromium capability tests][cap-tests]); allowed destinations still receive the original arguments unchanged. Paraphrases, unregistered values, other encodings such as base64 and remaining structured channels remain residual risks.

The fixture's native `nostream` tag and output projection keep model replies and private inputs out of its collected stream data; these are graph choices, not runtime redaction guarantees. Core still rejects non-allowlisted interaction URLs before pending publication, but an interrupt's raw update/checkpoint can contain its props. Hosts must not render raw streams and must keep private checkpoints/recovery stores on-device under the app/principal scope. Public errors use fixed text; SDK failure paths under review do not attach raw causes. Host-only diagnostic error objects are a separate evidence channel, not an exception permitting their export.

The corpus adds no runtime control and establishes no real-model or real-device result. Broader M4 release duties, host policy deployment, model/download limitations, external developer trials and device demonstrations remain governed by the brief and existing milestone exit records.
